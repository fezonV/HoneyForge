# BE-04 foundation

This document tracks the implemented BE-04 foundation and the work still needed for a complete deployment. The BE-03 runtime and final Low/Medium templates are merged into `dev`; issues #3 and #9 are complete. See [BE-03 acceptance](BE03_ACCEPTANCE.md) and [operator/profile acceptance](FE101_103_ACCEPTANCE.md).

## Event query API

The control API now exposes authenticated event search at `GET /api/v1/events`, filtered by `trap_id`, `from`, `to`, `source_ip`, `event_type`, and `session_id`, with keyset pagination. `GET /api/v1/sessions/{id}/timeline` returns a chronological page for an existing visitor session. `GET /api/v1/events/summary` requires a `from` and `to` period and returns event counts, event-type counts, distinct source count, and the top ten sources.

Ordinary event pages and details omit payloads entirely because the payload schema may contain user-entered credentials in arbitrary fields. `GET /api/v1/traps/{trap_id}/events/{event_id}/sensitive` returns the raw payload only to an operator and writes an `event.sensitive_read` audit entry before the response is sent. CSV export is operator-only, bounded to 10,000 rows, includes metadata only, and prefixes spreadsheet formula cells with an apostrophe.

`GET /api/v1/ws` accepts authenticated viewer and operator sessions only when the request `Origin` exactly matches `PUBLIC_ORIGIN`. It emits committed event, session, trap status, and command changes without event payloads. Logout closes that session's WebSocket connections immediately, and active connections recheck session validity every 30 seconds. Each client has a 64-message queue; a slow client is disconnected when full. Notifications are an in-process fanout for the single-control Compose baseline. Clients should reconnect and reconcile from persisted REST event pages using event IDs to avoid duplicate rows. Agent heartbeats publish online and service-state changes; offline state is derived from `last_seen`, so clients should refresh after reconnect.

Local GeoIP enrichment is optional. Set `GEOIP_CITY_DB` and/or `GEOIP_ASN_DB` to paths inside the control container, and set `GEOIP_SOURCE` and `GEOIP_VERSION` to the pinned data release. Mount the database directory read-only. Country, ASN, and the pinned release are stored with each new event; private, loopback, link-local, multicast, and missing addresses have no enrichment. The database files are not included in the repository or bundle.

## Secure center Compose baseline

`deploy/compose.yaml` adds a TLS Nginx façade with separate operator and agent listeners. The operator listener serves the built React application and proxies `/api/v1/`, including WebSocket upgrades. `Dockerfile.web` builds the locked npm dependencies and the shared preview templates; the runtime contains only static output, without source maps. Page reloads use the SPA fallback, while missing assets return 404. Web has its own internal frontend network, no database or management network and no published ports. Raw control and PostgreSQL ports are not published. PostgreSQL and control share an internal backend network; Nginx and control share an internal management network. The public edge network contains only Nginx. The `attack` network is reserved; deployed decoys use their own bundle networks.

The agent listener proxies only `/agent/v1/`. Control validates both JSON enrollment tokens and Bearer credentials; the proxy does not replace credential validation. Authentication failures and unknown routes return an ordinary HTML 404 without the Control request ID or JSON error schema. Successful authenticated responses pass through. An operator cookie does not authenticate this listener. Invalid credentials are deliberately reported to agents as a generic 404; investigate enrollment history/operator audit rather than expecting the public facade to explain authentication failures.

The Compose file uses Docker secrets for the PostgreSQL password, control database URL, and TLS key pair. Copy `deploy/.env.example` to `deploy/.env`, create the referenced secret files, and use a certificate whose host name matches `PUBLIC_HOST`:

```sh
mkdir -p deploy/secrets
umask 077
openssl rand -hex 32 > deploy/secrets/postgres_password
```

Write the matching PostgreSQL URL to `deploy/secrets/control_database_url` and place the trusted certificate and private key at the paths configured in `deploy/.env`. Set `HF_SOURCE_REVISION` to the full Git commit SHA being deployed; the bundle pins its remote build to this revision. Start the center with:

```sh
docker compose --env-file deploy/.env -f deploy/compose.yaml up --build -d
```

Before startup, ensure the secret files are readable by the container users. A file created with host mode 0600 is not automatically readable by an unrelated container UID: Compose local file secrets are bind mounts. Keep `deploy/secrets` private on the host (0700); give the TLS key owner UID/GID 101:101 and mode 0400 for Nginx. Give the database URL file the UID/GID of `honeyforge` in the built control image and mode 0400 (`docker run --rm --entrypoint id <control-image> honeyforge` shows it). Do not make the directory world-readable or mount the CA private key. The PostgreSQL entrypoint reads its password secret before dropping privileges.

Validate configuration with `docker compose --env-file deploy/.env -f deploy/compose.yaml config --quiet`, then add `--wait` to startup to require all healthchecks. Create the first user with `docker compose --env-file deploy/.env -f deploy/compose.yaml exec control /usr/local/bin/honeyforge-control -create-user`. Trust the CA through a verified channel and open `https://PUBLIC_HOST:8443` (use the configured port). Configure Low and Medium profiles/instances in the UI and run their downloaded bundles with separately issued enrollment tokens, following [FE2-01](FE201_ACCEPTANCE.md). Set `AGENT_ORIGIN` using `PUBLIC_HOST` and port 9443 to a name reachable from those hosts, with a matching certificate; loopback binds are for local access only.

Both published ports bind to loopback by default. For a remote host, set explicit bind addresses and restrict port 8443 to operators and 9443 to enrolled-agent networks with the host firewall. Never attach decoys to the management or backend networks. Agents use system certificate trust by default; a private CA can be added with the agent's `-ca-file` option or `HF_CA_FILE` environment variable.

## Remaining deployment work

`GET /api/v1/traps/{id}/bundle` now returns an operator-only, audited ZIP from the trap's desired immutable revision. It contains the decoy config, an isolated Compose layout, random local IPC secrets generated by the installer, and a pinned source checkout. The enrollment token is issued separately and entered during installation. The bundle includes synthetic visitor credentials, so protect the archive as operator data. Downloading it does not claim that an agent has enrolled or that the service is running.

The secure center stack includes the web UI; production center deployment remains a separate acceptance step. The generated bundle has been exercised through its real installer and Docker Compose on a separate containerized Linux node; see [FE2-01 acceptance](FE201_ACCEPTANCE.md). Final profile templates from #9 are integrated and accepted. The profile constructor and lifecycle UI are also accepted in FE1-01/02/03; the complete event journal/dashboard remain issues #12/#13. Verify Low and Medium, TLS validation, network reachability, queue replay after reconnect, and status reconciliation before closing BE-04.

## Network probes and restoration

On the prepared Linux host, set `HF_OPERATOR_URL`, `HF_AGENT_URL` to the two HTTPS origins and `HF_CA_FILE` to the verified CA PEM, then run `sh scripts/test-be04-deployment.sh`. It requires Docker Compose v2, curl, OpenSSL and grep. It checks page reloads, authenticated API rejection, unknown/invalid-credential agent requests, wrong CA and private listener reachability from a disposable internal attack network. It neither provisions users nor changes stored application data. It pulls `alpine:3.22` for network probes and removes only its own temporary network/files. This probe does not prove a physical production firewall: repeat from the actual attack host against published addresses and record both negative probes and successful authenticated agent traffic.

For a full acceptance, keep IDs of genuine Low/Medium requests and their agent/event identities. Verify filtered REST history and session timeline, disconnect/reconnect the browser WS and reconcile the same identities without duplicate rows. Interrupt the agent management connection, create events, restart the agent, restore connectivity and verify durable queue replay. Stop one decoy and check its agent remains online and the other decoy still serves requests. Verify wrong hostname and expired certificates fail as well as the automated wrong-CA probe.

Back up PostgreSQL with `docker compose --env-file deploy/.env -f deploy/compose.yaml exec -T postgres pg_dump -U <database-user> -d <database-name> -Fc > backup.dump` on a POSIX shell; protect the dump as sensitive operator data. Stop agents before copying their private queue/state volumes and runtime configuration; preserve ownership and permissions. For restart testing, use `docker compose ... restart` or `down` followed by `up --wait`; **never use `down -v`**, which deletes the database. Check the same profiles, revisions, sessions and event IDs after restart. For recovery into a new empty database, restore with `pg_restore` before starting control; control applies pending migrations on startup. Restore the stopped agent's private state/queue before resuming it. A lost permanent credential requires re-enrollment; losing a queue loses its unacknowledged events. Record actual host/Docker versions, deployed revision/image digests, commands and results in the [acceptance record](BE04_ACCEPTANCE.md).

TLS protects content in transit, not destination addresses, timing or traffic volume. Neutral service names and the HTML facade address an unauthenticated visitor; root access to a shared host, Docker daemon compromise and container escape are outside that claim. Do not route decoys to production networks or attach them to backend/management; generated bundles isolate decoy, visitor gateway and agent and never mount a Docker socket.

## Local full-stack regression

`AGENT_HOST` optionally supplies a separate certificate-covered DNS name for the agent origin; it falls back to `PUBLIC_HOST`. On Docker Desktop, a local operator can use `PUBLIC_HOST=localhost` and `AGENT_HOST=host.docker.internal`, with both names in the certificate SAN. Keep both published ports bound to loopback; the local regression uses ports 18443/19443 and visitor ports 28080/28081.

For a disposable initialized center, build `honeyforge-agent:be04` using `Dockerfile.agent` and `honeyforge-decoy:be04` using `Dockerfile.decoy`, run `npm ci --prefix web`, and provision a disposable operator. Store its username/password as JSON in the ignored `deploy/secrets/operator.json` and the trusted CA at `deploy/secrets/ca.pem` (or set `HF_OPERATOR_CREDENTIALS_FILE` and `HF_CA_FILE`). Run `node scripts/test-be04-stack.mjs`, with Docker CLI in PATH; optional `HF_OPERATOR_URL` and `HF_VISITOR_BASE_PORT` override the defaults. Python 3 is used only to extract the downloaded ZIP; on Windows the default is `py`, elsewhere `python3`, override with `HF_PYTHON` if needed.

The test creates real profiles/traps, downloads bundles and runs their unchanged manifests with a separate local-image override. It validates TLS enrollment, IPC apply, Low/Medium visitor actions, session timeline, WebSocket, management outage, queue replay after agent restart, component independence and persistence across a center/PostgreSQL restart. It intentionally stops/restarts the disposable center. Success leaves the sample deployments running and writes a private `result.json` with their IDs/Compose arguments under `deploy/secrets/stack-<run-id>`; failure removes only that run's sample containers/networks and retains volumes/evidence. This uses local prebuilt images and does **not** replace testing the pinned-source `install.sh` on a separate prepared Linux host. Do not run it against a shared or production center.

## Independent Docker node and egress policy

For the actual installer regression, prepare a disposable Linux node with its own Docker Engine and `git`, `openssl`, `unzip`, `stty`. The optional containerized fixture is `docker:28-dind`, started privileged with a Unix-only dockerd listener and no mount of the parent's Docker socket. Publish only the chosen visitor ports to host loopback. For example, create `hf-be04-linux-node` with `-p 127.0.0.1:28180:28180 -p 127.0.0.1:28181:28181` and `dockerd --storage-driver=overlay2 --host=unix:///var/run/docker.sock`. This is a disposable test node, not a production isolation boundary.

Set `HF_BUNDLE_NODE=hf-be04-linux-node` and `HF_VISITOR_BASE_PORT=28180`, then run the same `node scripts/test-be04-stack.mjs`. It copies the genuine operator-downloaded ZIP, separately issued token and verified CA to that node, invokes the ZIP's actual `install.sh`, clones its pinned GitHub source, builds images on the independent engine and runs the full scenario. It does not rewrite the generated manifest or substitute local images. The inner visitor bindings are 0.0.0.0, while the outer fixture publishes them on loopback. The center origin must be reachable from the node and match the leaf SAN; the local run used a verified private IPv4 management endpoint. Full installer logs and result IDs stay in the ignored per-run directory.

Each ZIP now includes `restrict-egress.sh`. On a prepared **IPv4 iptables Docker host**, run it as root from that bundle directory after creating its containers and before accepting the deployment. It finds only that bundle's management network, resolves the configured center, creates a dedicated chain and allows that subnet only to the center's TCP port. It attaches to both `DOCKER-USER` (forwarding) and `INPUT` (host-local destinations). The two private agent/decoy IPC interfaces are unaffected. Repeat application is idempotent; it does not flush global Docker/firewall rules. Before removing or recreating that bundle's networks, run `sh restrict-egress.sh remove`; it removes only its own jumps/chain and retains the application volumes.

This helper deliberately fails for IPv6-enabled management networks or a missing `DOCKER-USER` backend. It is not a universal nftables/IPv6 policy manager. It pins resolved IPv4 destinations; review DNS behavior in the target environment, reapply after center DNS changes and configure persistence/reapplication after Docker or host restart using host administration. It does not configure operator/agent ingress ACLs. The installer does not silently claim that the firewall is installed; host firewall preparation and its persistence are part of target-host acceptance.

For a containerized fixture with Python 3 and tcpdump installed, set `HF_STACK_RESULT` to the successful independent-node run's private `result.json` and run `py scripts/test-be04-node-security.py` on Windows (`python3` on Linux). This driver is for a disposable lab only: it inspects live users, caps, PID/IPC namespaces, resources, secrets/mounts and state modes; creates two reachable synthetic destinations; applies/removes/reapplies the policy; requires forbidden forwarding and host-input connections to fail while center connectivity works; and captures a short management TLS trace privately. It removes only its fixture servers. A successful run leaves the tested Low policy applied. The capture demonstrates encrypted application records in that trace, not hidden destination IPs or timing.

Use standards-compliant local certificates. In particular, Python 3.13's strict verifier requires the CA's critical `basicConstraints=CA:TRUE` and `keyUsage=keyCertSign,cRLSign`; the leaf needs the correct SAN, serverAuth, CA:FALSE and digitalSignature/keyEncipherment usages. Check the leaf with `openssl verify -x509_strict -CAfile ca.pem tls.crt`. Keep the CA private key out of containers and source control; do not bypass chain or hostname verification to compensate for a malformed certificate.
