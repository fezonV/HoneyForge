# Приёмка FE1-01, FE1-02 и FE1-03

Проверка 15 октября 2026 года для issues #5, #7 и #8. Код жизненного цикла
профилей из PR #34 интегрирован с актуальным `dev` и дополнен исправлениями
мастера, API-клиента и проверками. Этот документ подтверждает указанные задачи;
общая сдача проекта, deployment центра и независимые QA-пакеты остаются отдельными.

## Среда и воспроизведение

Linux, Go 1.27.2, Node.js 24.19.0, PostgreSQL 17 в отдельном контейнере,
Playwright/Chromium. База одноразовая; реальные пользовательские данные не нужны.
Сквозные сценарии запускают настоящий Control API, TLS-канал агентов и отдельные
бинарные процессы Low/Medium. Они не подменяют API ответами fixtures.

```sh
npm --prefix web ci
cd web && npx playwright install chromium && cd ..
export TEST_DATABASE_URL='postgres://postgres:<test-password>@127.0.0.1:55432/honeyforge_test?sslmode=disable'
npm --prefix web run build
npm --prefix web run lint
npm --prefix web run test:e2e
HF_DECOY_PROCESS_TEST=1 go test -race -short -count=1 ./...
go vet ./...
go build ./...
git diff --check
```

Без `TEST_DATABASE_URL` live-сценарии пропускаются. Для приёмки переменная
обязательна: пропуск не является успешной проверкой. Управляемые отказы API/WS
проверяются отдельно и не заменяют live-сценарии.

## Подтверждение критериев

| Задача | Проверка |
|---|---|
| #5: настоящий вход, operator/viewer, серверные запреты | `trap-park.spec.mjs`: живой вход и прямые 403 на изменение данных, enrollment, bundle и чувствительную revision; `trap-control.spec.mjs`: истечение сессии без повторного POST |
| #5: клиент проверяет ответы, ошибки различимы, нет автоматического fallback | `api-contract.spec.mjs`: неверный успешный JSON и неожиданный 204, 400/401/403/409/503; `validation.ts` проверяет потребляемые структуры до преобразования в UI-модель |
| #5: маршруты, WS и клавиатура | Сохранение исходного hash при повторном входе, закрытие WS при выходе, Tab/Shift+Tab/Escape и возврат фокуса; проверки и снимки 1440×900 и 1280×720 |
| #5: клиент событий и сессий | Live-сценарий вызывает типизированные page/detail/timeline/exportCsv; фильтр читает реальные события, timeline содержит связанные действия, CSV содержит выбранную ловушку |
| #7: Low/Medium создаются через UI | `wizardProfile` в `trap-park.spec.mjs`: заполнение настоящего мастера и сохранение через API; создание профиля не создаёт экземпляр |
| #7: параметры и валидация | Корректные относительные пути по умолчанию и в генераторе файлов; пределы UTF-8, credentials, файлов, целых портов и интервалов; ошибки сервера возвращают на нужный шаг; обязательные категории и TLS нельзя отключить |
| #7: реальные настройки и безопасный preview | Medium создан мастером; реальный вход и чтение файлов проверяют содержимое применённой revision; `profile-preview.spec.mjs` проверяет XSS, пустые данные и отсутствие credentials/сетевых обращений в iframe |
| #8: копия и редактирование | Копия получает отдельный ID и v1; оператор явно читает sensitive revision для копирования/редактирования, пароли не попадают в общий cache или browser storage; изменение оригинала сохраняет копию и её историю |
| #8: версии и сравнение | История immutable revisions, сравнение сервисов/баннеров, всех видимых текстов, содержимого файлов, logging/channel; пароли скрыты и не выдаются за сравнимые значения |
| #8: конкурентное сохранение | Другой редактор создаёт v2 в настоящем API; сохранение устаревшей v1 получает 409, черновик остаётся; новая v3 создаётся только после явного переноса правок |
| #8: удаление | Занятый профиль блокируется UI и прямым API 409; после отвязки профиль удаляется из каталога, историческая revision остаётся доступной; серверная гонка 409 обновляет связанные экземпляры |
| #8: конкретная revision и независимость | Историческая v1 передаётся в мастер экземпляра; сохранение v2 не переназначает A/B; после отдельного применения A отдаёт новый файл, B сохраняет старое содержимое и credentials |

## Результаты

- Frontend typecheck/build — успешно.
- ESLint — 0 ошибок, 35 предупреждений; предупреждения `any` и Fast Refresh

## Границы

API/WS-отказы, некорректный JSON и клиентские состояния проверяются управляемыми
ответами браузерных тестов; реальные изменения профилей, конфликты, роли,
пароли, файлы и события подтверждаются отдельными live-сценариями.

Две копии одного Medium в процессном тесте слушают разные loopback-адреса и
используют отдельные config/SQLite/IPC. Настоящий Docker installer имеет свою
приёмку в FE201_ACCEPTANCE.md. Внешний firewall, полный Compose центра с UI,
длительный разрыв связи и независимая финальная QA-приёмка этим прогоном не
закрываются. В UI не заявляются неподдерживаемые jitter, mTLS или смена имени
процесса; изменение портов требует подготовки нового deployment.
