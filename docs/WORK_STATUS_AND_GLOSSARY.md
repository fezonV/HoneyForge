# Что сделано в HoneyForge и словарь терминов

Этот документ объясняет текущее состояние репозитория простым языком: какие изменения внесены, как устроена добавленная серверная основа, чем она проверена и какие части проекта ещё впереди. Технические имена полей, программ, переменных и маршрутов оставлены в оригинальном виде, чтобы их можно было найти в коде.

## Коротко о результате

В проект добавлен первый серверный этап BE-01 — основа управляющего сервера HoneyForge. До этого в корне был небольшой демонстрационный сервер: он показывал фиктивный архив и панель событий, а сами события хранил только в памяти. Теперь рядом с ним есть отдельное приложение `cmd/control`: оно хранит пользователей, профили, ловушки, регистрации агентов, команды и аудит в PostgreSQL.

Новый сервер пока не запускает сами приманки и не доставляет события от них. Он позволяет подготовить и хранить их настройки, зарегистрировать экземпляр, назначить ему конкретную версию профиля и поставить команду в очередь. Получение команды работающим агентом и подтверждение её исполнения — следующие этапы.

Код находится в отдельной ветке `codex/be-01-control-foundation`, основанной на `dev` и отправленной на GitHub. Коммит: `9e7a6a6` (`feat(be-01): add control API foundation`). В `main` изменения не сливались.

## Что добавлено

### Отдельный управляющий сервер

Точка запуска — [`cmd/control/main.go`](../cmd/control/main.go). Это отдельное приложение, старый пример из корневого `main.go` сохранён. Разделение позволяет развивать полноценный центр, не ломая демонстрационную страницу и её локальный журнал.

При запуске управляющий сервер проверяет соединение с базой и применяет миграции. Он по умолчанию слушает `127.0.0.1:8081`, задаёт ограничения HTTP-сервера и корректно завершает работу по сигналу остановки. Для начальной настройки операторов предусмотрена команда `-create-user`; встроенной стандартной учётной записи нет.

### Контракты и API

[`api/openapi.yaml`](../api/openapi.yaml) описывает форматы запросов и ответов. Папка [`examples`](../examples) содержит примеры профиля, ловушки, команды и будущих сообщений событий, сессий и WebSocket.

Действующие маршруты сгруппированы по назначению:

| Маршруты | Назначение |
|---|---|
| `/healthz`, `/readyz` | Проверить, что сервер работает и что доступна база данных |
| `/api/v1/auth/*` | Войти, выйти и узнать текущего пользователя |
| `/api/v1/templates` | Получить список поддерживаемых шаблонов Low и Medium |
| `/api/v1/profiles` | Создавать, читать, менять, удалять профили и просматривать версии |
| `/api/v1/traps` | Создавать и просматривать ловушки, назначать им версии профиля |
| `/api/v1/traps/{id}/enrollment-token` и `/agent/v1/enroll` | Выпускать одноразовый код регистрации и обменивать его на учётные данные агента |
| `/agent/v1/traps/{id}/config` | Агенту — читать конфигурацию, назначенную именно его ловушке |
| `/api/v1/traps/{id}/commands` | Ставить команды в очередь и просматривать их состояние |
| `/api/v1/audit` | Оператору — читать журнал значимых действий |

Схемы событий, сессий посетителей и WebSocket тоже описаны в OpenAPI, чтобы фронтенд, агент и следующие этапы могли согласовывать форматы. Самих маршрутов приёма событий, истории событий или WebSocket-подключения пока нет.

### Хранение и модели данных

Миграция [`migrations/001_init.sql`](../migrations/001_init.sql) создаёт таблицы пользователей, сессий операторов, профилей, версий профилей, ловушек, агентов, кодов регистрации, команд, событий, сессий посетителей и аудита. Выполнение миграций устроено в [`migrations/migrate.go`](../migrations/migrate.go).

Профиль хранит не только заголовок страницы. В его конфигурации есть уровень Low или Medium, шаблон, HTTP-службы и порты, баннеры, тексты, синтетические имена и пароли, фиктивные файлы, категории журналирования и настройки канала.

Когда оператор меняет профиль, сервер добавляет новую неизменяемую версию. Старые версии не перезаписываются. Ловушка хранит две отдельные ссылки: желаемую версию, которую оператор назначил, и применённую версию, которую в будущем подтвердит агент. Сейчас сервер не выдумывает подтверждение: после назначения `applied_revision` остаётся прежней или пустой.

Ловушку можно логически удалить, не стирая связанные исторические данные. Профиль нельзя удалить, пока он назначен хотя бы одной ловушке. После отвязки он помечается удалённым, а его версии остаются доступны для истории.

### Вход, роли и защита

Пользователь входит по имени и паролю. Пароль хранится в виде bcrypt-хеша. После входа сервер создаёт случайную сессионную cookie; в базе лежит только её SHA-256-хеш. Срок сессии — восемь часов, выход отзывает её. Попытки входа ограничиваются.

Есть две роли:

- `operator` — может изменять профили и ловушки, выпускать коды регистрации, ставить команды и читать чувствительные сведения;
- `viewer` — может читать обычные данные, но сервер запрещает ему изменяющие операции и доступ к чувствительным сведениям.

Изменяющие запросы защищены CSRF-проверкой: браузер отправляет CSRF-cookie и то же значение в заголовке `X-CSRF-Token`. Если запрос содержит `Origin`, сервер сравнивает его с настроенным `PUBLIC_ORIGIN`. Обычные ответы скрывают синтетические пароли; отдельный запрос чувствительной версии доступен только оператору и записывается в аудит.

Коды регистрации действуют десять минут и принимаются один раз. После обмена случайный токен агента возвращается для сохранения на стороне агента; в базе центра сохраняется только его SHA-256-хеш. Каждый такой токен привязан к одной ловушке, поэтому он не даёт агенту читать конфигурацию другой.

Эти механизмы относятся к Control API. Полностью настроенный TLS-канал между центром и будущим отдельным процессом агента, а также изоляция сетей ещё не реализованы.

### Проверка профилей и запросов

В [`internal/contracts/types.go`](../internal/contracts/types.go) находятся структуры запросов и ответов и валидатор конфигурации профиля. Сейчас сервер принимает только HTTP-службы, ограничивает размеры текстов, списков и файлов, проверяет диапазоны портов и требует безопасные относительные пути для фиктивной файловой системы. Профиль Medium обязан содержать нужные ему категории журналирования. Неподдерживаемая конфигурация отклоняется до записи.

Запросы разбираются с запретом неизвестных JSON-полей и ограничением размера тела. Списки профилей, ловушек, команд и аудита разбиваются на страницы; фильтры и параметры проверяются сервером. У каждой ошибки API есть код, понятное сообщение и идентификатор запроса.

### Аудит и очередь команд

Сервер записывает важные операции: вход и выход, изменение профиля, назначение версии, регистрацию агента, выпуск команды и чтение чувствительных данных. Пароли и токены не должны попадать в аудит.

Команда имеет собственный `command_id`, срок действия, тип (`start`, `stop` или `apply_profile`) и ожидаемое состояние профиля. В BE-01 команда сохраняется в PostgreSQL со статусом `queued`; просроченные записи могут отображаться как `expired`. Сам центр пока не отправляет команду агенту, а статусы `delivered`, `applied` и `failed` появятся по мере реализации агента и приманки.

### Локальный запуск

Файлы [`.env.example`](../.env.example), [`Dockerfile.control`](../Dockerfile.control), [`compose.yaml`](../compose.yaml) и [`.dockerignore`](../.dockerignore) готовят локальное окружение. Compose задаёт PostgreSQL с постоянным томом и управляющий API; порты публикуются на loopback. В примере `.env.example` нет настоящего пароля — перед запуском нужно задать свой.

Для запуска без Compose потребуется PostgreSQL и Go 1.26 или новее:

```powershell
$env:DATABASE_URL = 'postgres://honeyforge:<ваш-пароль>@127.0.0.1:5432/honeyforge?sslmode=disable'
$env:PUBLIC_ORIGIN = 'http://127.0.0.1:8081'
$env:COOKIE_SECURE = 'false' # только для локального HTTP на loopback
go run ./cmd/control -create-user
go run ./cmd/control
```

Перед запуском нужно создать пользователя. Интерактивный ввод пароля не отображает его на экране. Для проверки интеграций задают `TEST_DATABASE_URL`, причём он должен указывать на отдельную тестовую базу, а не на пользовательскую или рабочую.

## Что проверено

Интеграционный набор [`internal/control/control_integration_test.go`](../internal/control/control_integration_test.go) проверяет работу с PostgreSQL, роли, CSRF, одновременные изменения одной версии, назначение нескольких ловушек, удаление и историю, выпуск и повторное использование кодов регистрации, привязку токена агента, команды, фильтры и курсоры. Используется отдельная схема со случайным именем; тест удаляет её, а не всю базу.

Также проверены перезапуск центра и базы, сохранение профиля, версии, назначения, сессии и аудита, а также ответы готовности при остановленной и работающей базе. Для документации BE-01 зафиксирован успешный прогон `go test -race` с PostgreSQL, `go vet`, `go build` и проверка OpenAPI Redocly без ошибок.

После переноса ветки на обновлённый `dev` повторно прошли `go test -race`, `go vet` и `go build`. При повторном прогоне PostgreSQL-интеграционные тесты пропустились, потому что тестовая БД не была доступна. Docker в среде также отсутствовал, поэтому Compose-образ не собирался. Подробная матрица находится в [`docs/BE01_ACCEPTANCE.md`](BE01_ACCEPTANCE.md).

## Что осталось

| Задача | Текущее состояние |
|---|---|
| BE-01 / issue #1 — основа центра | Реализованы и проверены профили, версии, доступ, база, аудит, реестр ловушек, регистрация агента и очередь команд. Работа опубликована отдельной веткой, не слита в `main`. |
| BE-02 / issue #2 — агент и доставка | Впереди: исполняемый `cmd/agent`, heartbeat, локальная постоянная очередь, доставка и подтверждение событий, получение и повторобезопасное выполнение команд. |
| BE-03 / issue #3 — приманки | Впереди: `cmd/decoy`, реальные HTTP-сценарии Low/Medium, вход с синтетическими данными, отдельные сессии, фиктивные файлы и связанные события. |
| BE-04 / issue #4 — развёртывание и наблюдение | Впереди: полноценное разделение сетей и процессов, TLS-приёмка, комплект развёртывания, API истории событий, WebSocket и сводки. |

Поэтому текущий результат — не готовая система приманок и доставки, а сохранённая демонстрация плюс работающий фундамент Control API. Полную демонстрацию проекта можно принять только после интеграции и проверки задач #2–4 вместе с интерфейсом и тестированием.

## Словарь терминов

| Термин | Простое объяснение |
|---|---|
| **Honeypot / ловушка / приманка** | Изолированный сервис, который выглядит правдоподобно и записывает действия посетителя для анализа. В проекте «ловушка» — экземпляр, а «приманка» — запущенная внутри него служба. |
| **Control API / управляющий API** | Серверные HTTP-маршруты, через которые оператор управляет профилями и ловушками, а агент получает назначенные ему данные. |
| **Agent / агент** | Отдельный процесс рядом с приманкой. В будущем он будет связывать приманку с центром: получать команды и надёжно отправлять события. Сейчас есть только регистрация агента и чтение им конфигурации. |
| **Decoy / приманка-сервис** | Сама служба, с которой взаимодействует посетитель. В BE-01 её рабочего процесса ещё нет. |
| **Template / шаблон** | Поддерживаемый тип приманки и начальная форма настроек, например Low HTTP или Medium HTTP. |
| **Profile / профиль** | Настройки конкретного варианта приманки: служба и порт, видимые тексты, фиктивные учётные данные, файлы и правила журналирования. Один профиль можно назначить нескольким ловушкам. |
| **Revision / ревизия / версия** | Снимок профиля на определённый момент. Изменение создаёт новый номер версии, старую запись не переписывает. |
| **Trap / экземпляр ловушки** | Конкретная установка, созданная на основе профиля. У неё есть собственный идентификатор, привязка порта, агент и состояния. |
| **Desired revision / желаемая версия** | Версия профиля, назначенная оператором экземпляру. Она может отличаться от фактически работающей. |
| **Applied revision / применённая версия** | Версия, которую агент и приманка действительно приняли и подтвердили. Одного назначения недостаточно, чтобы считать её применённой. |
| **Event / событие** | Запись об одном действии: например, HTTP-запросе, попытке входа или чтении фиктивного файла. Сам запрос не доказывает, что произошло вторжение. |
| **Session / сессия посетителя** | Связанные действия одного посетителя во времени, например вход, просмотр файла и ввод псевдокоманды. В BE-01 только описана схема; запись сессий появится вместе с приманкой и агентом. |
| **Command / команда** | Запрос центра к экземпляру (`start`, `stop`, `apply_profile`). Записанная в очередь команда ещё не означает, что агент её получил или выполнил. |
| **`command_id`** | Уникальный номер команды, по которому центр и агент смогут узнавать её при повторной доставке или подтверждении. |
| **Enrollment / регистрация агента** | Первоначальный обмен одноразового кода на отдельный токен агента, привязанный к конкретной ловушке. |
| **Token / токен** | Случайная строка, подтверждающая право на доступ. Сессионный токен оператора и токен агента разные и дают разные полномочия. |
| **Hash / хеш** | Односторонний отпечаток строки. Сервер сравнивает хеш предъявленного токена с сохранённым хешем; исходный токен из базы восстановить нельзя. Пароли обрабатываются специальным алгоритмом bcrypt. |
| **Cookie** | Небольшое значение, которое браузер хранит для сайта и автоматически отправляет с запросами. `HttpOnly` скрывает cookie от обычного JavaScript страницы, а `Secure` требует HTTPS. |
| **Session cookie / cookie сессии** | Cookie, которая подтверждает вход оператора. В этом проекте серверная сессия действует восемь часов и может быть отозвана при выходе. |
| **CSRF** | Подделка запроса от имени уже вошедшего пользователя через его браузер. Проверка cookie и заголовка `X-CSRF-Token`, а также `Origin` помогает отвергать такие запросы. |
| **Origin** | Источник веб-запроса: схема, имя узла и порт. Сервер сверяет заголовок `Origin` с `PUBLIC_ORIGIN` для изменяющих операций. |
| **RBAC / роль** | Проверка прав по роли пользователя. Здесь `operator` изменяет данные и видит разрешённые секреты, а `viewer` может только просматривать обычные данные. |
| **Audit / аудит** | Защищённый журнал действий операторов и важных операций. Он помогает выяснить, кто и когда изменил настройки. Пароли и токены туда не записываются. |
| **Migration / миграция базы** | Версионированный SQL-сценарий для создания или изменения таблиц. При запуске центра миграции применяются к PostgreSQL. |
| **PostgreSQL** | Реляционная база данных, где постоянно хранятся пользователи, профили, ревизии, ловушки, команды и аудит. В отличие от старого журнала в памяти, данные переживают перезапуск. |
| **Parameterized SQL / параметризованный запрос** | Запрос к базе, где значения передаются отдельно от текста SQL. Это защищает от подстановки введённого текста как команды базы. |
| **JSONB** | Тип PostgreSQL для хранения JSON с возможностью индексировать и обрабатывать его на стороне базы. Используется для конфигурации профиля и структурированных подробностей. |
| **Soft delete / логическое удаление** | Запись помечается удалённой, но физически остаётся в базе, чтобы сохранить историю и связи. |
| **Pagination / пагинация** | Выдача большого списка небольшими страницами. Клиент запрашивает следующую страницу по курсору, а сервер ограничивает максимальное число записей. |
| **Cursor / курсор** | Непрозрачное значение, показывающее, с какого места читать следующую страницу списка. Это не номер страницы и не идентификатор доступа. |
| **Filter / фильтр** | Параметр списка, который оставляет только записи, подходящие условию, например ловушки с нужным профилем или статусом. |
| **TTL** | «Время жизни» записи. По истечении срока команда считается просроченной и не должна исполняться. |
| **`queued` / очередь** | Команда записана центром и ждёт доставки. Этот статус не означает, что агент её получил. |
| **`delivered` / доставлено** | Будущий статус: агент получил команду. В текущей версии доставка ещё не реализована. |
| **`applied` / применено** | Будущий статус: приманка подтвердила изменение конфигурации или выполнение действия. Центр не должен выставлять его заранее. |
| **ACK / подтверждение** | Ответ получателя, подтверждающий, что данные приняты и сохранены. Для событий центра подтверждение должно отправляться после фиксации записи в базе. |
| **Idempotency / идемпотентность** | Свойство, при котором повтор одной и той же команды или события не создаёт повторный побочный эффект или дубликат записи. |
| **Deduplication / дедупликация** | Поиск и подавление повторов по уникальному ID события, например по паре `(agent_id, event_id)`. В BE-01 приём событий ещё не добавлен. |
| **Durable queue / постоянная очередь** | Очередь на диске, которая переживает перезапуск процесса. Нужна агенту, чтобы не потерять события при обрыве связи с центром. |
| **Heartbeat / проверка связи** | Периодический сигнал агента центру. По времени последнего сигнала центр сможет оценить доступность агента. Это относится к BE-02. |
| **Fake-FS / фиктивная файловая система** | Набор придуманных файлов внутри приманки. Посетитель видит только их; код не должен читать настоящие файлы хоста. |
| **Telemetry / телеметрия** | События и показатели о том, что происходит в приманке, агенте и центре. |
| **REST API** | Набор HTTP-маршрутов, где клиент запрашивает или изменяет данные отдельными запросами. Основная часть текущего API устроена так. |
| **WebSocket** | Долгое двустороннее соединение для передачи обновлений сразу после события. В текущем коде есть только схема будущих уведомлений, самого WebSocket-сервера ещё нет. |
| **Health check (`/healthz`)** | Проверка, что процесс сервера жив и отвечает на запрос. Она сама по себе не гарантирует доступность базы. |
| **Readiness check (`/readyz`)** | Проверка, что сервер готов обслуживать запросы; сейчас она также проверяет соединение с PostgreSQL. |
| **TLS / HTTPS** | Шифрование соединения и проверка сертификата сервера. HTTPS используется для защиты передачи данных; проверка TLS между будущим агентом и центром будет частью BE-02/BE-04. |
| **Loopback (`127.0.0.1`)** | Сетевой адрес, доступный только с этого же компьютера. Локальная привязка Compose не открывает порт всем узлам сети. |
| **Docker Compose** | Инструмент запуска нескольких контейнеров и связанных служб из одного файла конфигурации. Файл подготовлен, но образ в нашей среде не собирался: Docker отсутствовал. |
| **Volume / том данных** | Постоянное хранилище Docker, которое остаётся после перезапуска контейнера и хранит данные PostgreSQL. |
| **OpenAPI** | Машиночитаемое описание HTTP API: маршрутов, параметров, схем запросов и ответов. Redocly проверяет, что файл схемы корректен. |
| **`go build`** | Компиляция проекта; проверяет, что код можно собрать. |
| **`go vet`** | Статический анализ Go-кода, который ищет распространённые ошибки. |
| **`go test -race`** | Запуск тестов со встроенной проверкой гонок: одновременного небезопасного обращения к общим данным. Для интеграционных тестов дополнительно нужна переменная `TEST_DATABASE_URL`. |
| **Branch / ветка Git** | Отдельная линия изменений. Ветка `codex/be-01-control-foundation` позволяет проверять BE-01 отдельно от `main` и от уже существующей ветки `dev`. |
| **Commit / коммит** | Зафиксированный набор изменений с уникальным номером и описанием. Текущий код BE-01 зафиксирован коммитом `9e7a6a6`. |
| **Push** | Отправка локальных коммитов и ветки в удалённый GitHub-репозиторий. BE-01 уже отправлен в отдельную ветку. |
| **Pull request (PR)** | Предложение включить ветку в другую ветку после просмотра изменений. Push ветки сам по себе не создаёт PR и не сливает код. |
