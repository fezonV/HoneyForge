# FE2-03: журнал событий и timeline

Ветка `codex/fe2-03`, основа — `dev` (`98ea569`). Используются существующие
контракты BE-04: REST query/detail/timeline, отдельный sensitive GET и WS.
В `origin/codex/be04-complete` проверены изменения размещения UI за reverse proxy;
они не меняют эти контракты. Ветка BE-04 в эту работу не объединялась.

## Что реализовано

- Журнал из PostgreSQL: trap/service, время с часовым поясом, IP/порты,
  protocol, тип, краткое описание и исторические profile_id/applied_revision.
- Все шесть фильтров передаются серверу вместе. Фильтры, cursor, выбранное
  событие и страница timeline сохраняются в URL; reload восстанавливает запрос.
- По 50 событий на странице, cursor-пагинация без ограничения первыми 100.
  Детали читаются отдельным GET. Timeline идёт от старых действий к новым,
  проверяет session_id/trap_id и не подставляет текущую версию профиля.
- Общий авторизованный WS инвалидирует REST-выборку. Reconnect перечитывает
  активные фильтры; дубли удаляются. Предыдущие запросы отменяются, устаревшие
  ответы не заменяют новый фильтр.
- Пауза, просмотр старой страницы или модального окна фиксируют читаемую
  выборку. Счётчик новых событий и явное обновление возвращают к свежим данным.
  Счётчик ограничен 1000 идентификаторами, при переполнении показано `+`.
  WS-данные не накапливаются и не служат хранилищем.
- Payload не загружается обычным GET. Только operator может явно запросить
  sensitive endpoint: решение и аудит выполняет сервер. Viewer не делает этот
  запрос; прямое обращение сервер запрещает. Текст не исполняется как HTML.
  Ответ ограничен 256 KiB, отображение — 16 384 символами, секреты не сохраняются
  в URL/browser storage. При закрытии/выходе данные сбрасываются.
- Loading/empty/error/disconnected, повторное чтение и закрытие WS при выходе.

## Автоматические проверки

На Windows 15 октября 2026 прошли сборка UI, lint (0 ошибок, 34 существующих
предупреждения), `go build ./...`, `go vet ./...` и выбранные Go-проверки событий,
прав и WS с PostgreSQL 17.11. Оба сквозных сценария выше прошли с настоящими
control/agent/decoy. Для Windows тестовый harness использует `.exe`, настраиваемый
`HF_TEST_PYTHON` и явный UTF-8 при чтении JSON из ZIP.
Также прошли 30 browser-сценариев журнала, общего API-клиента, управления,
realtime и предпросмотра профилей (последнему передаётся тот же Python).

Из `web/`:

```powershell
npm ci
npx playwright install chromium
npx playwright test e2e/events.spec.mjs
npm run build
npm run lint
```

Восемь контрактных browser-сценариев проверяют страницы старше 100, совместные
фильтры, race ответов, reconnect, pause, дубли, timeline, роли, ошибки и XSS.

Сквозная проверка требует **отдельную одноразовую PostgreSQL**, Go, Node.js,
OpenSSL в PATH и Python с модулем zipfile. `TEST_DATABASE_URL` должен указывать
на тестовую базу. Тест создаёт собственную схему и удаляет её после прогона.
Порты 8081 и 5173 должны быть свободны.

```powershell
$env:TEST_DATABASE_URL='postgres://postgres:<password>@127.0.0.1:55432/honeyforge_test?sslmode=disable'
# Если Python не доступен как python3:
$env:HF_TEST_PYTHON='C:\path\to\python.exe'
npx playwright test e2e/trap-park.spec.mjs --grep 'real Low/Medium|FE2-03'
```

Первый сценарий запускает настоящие control/agent/decoy, посещает Medium
(вход → файл → команда) и Low, проверяет появление в открытом журнале и timeline.
Второй использует 130 явно обозначенных исторических записей в PostgreSQL:
все фильтры, три страницы, reload, sensitive GET, запись аудита и viewer 403.
Установка Linux bundle через Docker остаётся отдельным существующим сценарием
`scripts/test-fe2-bundle.sh`; новый журнал включён в его browser-проверки.

## Ручная проверка

1. Запустите PostgreSQL, control и UI по инструкции в `web/README.md`.
   Войдите в режиме API. Создайте Low и Medium, запустите агенты/приманки.
2. Откройте «События», оставьте страницу открытой. В другом браузере посетите
   Low; в Medium войдите, откройте фиктивный файл и выполните псевдокоманду.
   Строки должны появиться без reload с правильными trap_id/service_id/revision.
3. Примените фильтры вместе, перейдите к старой странице и перезагрузите её.
   Проверьте сохранность фильтров и позиции cursor.
4. Откройте событие → timeline. Проверьте порядок действий и идентификаторы.
   Изменение текущего профиля не должно менять revision старого события.
5. Поставьте ленту на паузу и создайте новые обращения. Строки остаются на месте,
   появляется счётчик. Нажмите «Показать новые события».
6. Временно отключите сеть вкладки и восстановите: WS переподключится,
   REST восстановит выборку. Дубли строк не появляются.
7. В деталях operator нажмите «Запросить payload с аудитом» и проверьте аудит
   `event.sensitive_read`. Viewer видит только метаданные; HTML в payload — текст.
8. Выйдите из системы: диалоги закрываются, WS прекращает работу.

## Границы

Geo/ASN показываются только при наличии полей в API и настроенных серверных баз
GeoIP. Без них — «Неизвестно». Структурированного artifact-контракта и скачивания
артефактов сейчас нет; поле отмечено как неизвестное. Для этой возможности нужны
серверная модель, хранилище и разрешённый endpoint. Краткое описание основано на
event_type: обычный API намеренно скрывает весь payload, включая пути и команды.
Их текст доступен оператору при отдельном аудируемом раскрытии.

После объединения PR BE-04 нужно повторить проверку за итоговым TLS/reverse proxy
на целевом стенде: тот же origin, cookie авторизации и WebSocket upgrade.
