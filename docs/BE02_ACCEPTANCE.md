# BE-02: агент и надёжная доставка

Проверено 14 октября 2026 года на основе `dev` (`3511383`), Go 1.26.0 и
PostgreSQL 17. Итоговые изменения дополняют PR #22: журнал команд, проверка TTL,
изоляция циклов агента, приватная SQLite и доступная диагностика.

Полный `go test -count=1 ./...` с PostgreSQL, `go test -race -short -count=1 ./...`,
`go vet ./...`, `go build ./...` и `git diff --check` прошли. Оба изменённых
OpenAPI 3.1 контракта проверены валидатором; для IPC локальные ссылки на схемы
основного контракта предварительно объединены в памяти.

## Поведение

- Агент регистрируется одноразовым enrollment-токеном, сохраняет отдельный
  credential и обращается к центру по HTTPS с проверкой сертификата. Приватный
  CA добавляется через `-ca-file`. Redirect управляющего API запрещён, включая
  перенаправление на HTTP.
- Decoy передаёт события на отдельный IPC listener с отдельным токеном. ACK
  `202 persisted=true` возвращается после SQLite commit с `synchronous=FULL`.
  Основной файл, WAL и SHM имеют права `0600`; новые каталоги создаются с `0700`.
  Очередь и credential агента не монтируются в контейнер decoy.
- Очередь ограничена 10 000 записями, включая quarantine. Пакет содержит до
  100 событий. Локальное тело события ограничено 256 KiB; центр ограничивает
  тело пакета 1 MiB. Слишком большой пакет делится при доставке.
- Отправка выполняется раз в секунду. Первая ошибка допускает следующую
  попытку через обычный интервал отправки, далее задержка составляет
  4/8/16/32/64 секунды и остаётся ограниченной 64 секундами. Состояние попыток
  хранится в SQLite. Временные ошибки и ошибки авторизации сохраняют события.
- Неисправимые события изолируются делением пакета и переводятся в quarantine
  с причиной. Сюда входит `session_conflict`; остальные события продолжают
  доставляться. Записи quarantine не удаляются автоматически и занимают лимит
  очереди. При переполнении IPC возвращает `507`, при ошибке записи — `503`;
  decoy отказывает соответствующему действию без успешного локального ACK.
- Центр проверяет agent/trap по credential, сохраняет пакет транзакционно и
  подтверждает IDs после commit. Идентичный повтор `(agent_id,event_id)`
  подтверждается как duplicate; изменение содержимого вызывает конфликт.
- Доставка, heartbeat и последовательная синхронизация/обработка команд работают
  независимо. Зависшая доставка не блокирует heartbeat или локальный приём.
  Начальные интервалы: heartbeat 5 секунд, sync 2 секунды, команды 2 секунды;
  после чтения профиля heartbeat/sync используют его параметры. Центр считает
  агента offline через 20 секунд без активности; состояние службы независимо.
- Перед вызовом decoy агент проверяет TTL и сохраняет intent команды в SQLite.
  Deadline передаётся адаптеру. Результат записывается до отчёта центру,
  повторяется после потери ответа и переживает рестарт. Известный `command_id`
  не выполняется повторно; изменение его содержимого отклоняется.
- Успех `apply_profile` подтверждается только после совпадающего ответа decoy.
  Невалидная конфигурация не меняет рабочую конфигурацию и applied revision.
  Stop отключает обслуживание выбранной приманки; heartbeat и очередь остаются
  активны. Терминальный результат центра не превращается в expired при позднем
  повторе ACK.

## Диагностика

`GET /v1/status` на IPC listener требует тот же `Bearer`-токен, что и локальная
передача событий. Возвращает `queue_depth`, `queue_limit`, `quarantined`, причину
quarantine, счётчики отправки/ошибок/повторов и `degraded`. Payload посетителя,
синтетические пароли и управляющие токены в ответ не входят.

Агент передаёт эти же поля в heartbeat. Миграция
`005_agent_telemetry.sql` сохраняет последний снимок в ловушке; он доступен через
авторизованные `GET /api/v1/traps` и `GET /api/v1/traps/{id}` в поле `telemetry`.
До первого снимка поле отсутствует. При остановленной службе статус остаётся
`stopped`, а неисправность доставки видна отдельно в `telemetry.degraded`.
Для работающей службы проблемы очереди отражаются также статусом `degraded`.
Счётчики относятся к текущему процессу; глубина и quarantine восстанавливаются
из SQLite. Offline-снимок показывает последнее известное состояние.

## Запуск

Для полноценного размещения используйте bundle и TLS-инструкцию
[BE-04](BE04_FOUNDATION.md). Отдельный процесс агента можно запустить так:

```sh
go build -o ./agent ./cmd/agent
mkdir -m 700 -p ./.agent-private
./agent \
  -center https://control.example:9443 \
  -ca-file ./center-ca.pem \
  -trap '<trap UUID>' \
  -enrollment-token-file ./enrollment-token \
  -state ./.agent-private/state.json \
  -queue ./.agent-private/events.sqlite \
  -ipc-listen 127.0.0.1:9101 \
  -ipc-token-file ./decoy-agent-token \
  -decoy-admin http://127.0.0.1:9100 \
  -decoy-token-file ./agent-decoy-token
```

Адрес, CA, UUID и файлы токенов берутся из подготовленного стенда. При повторном
запуске уберите аргументы enrollment: используется приватный `state.json`.
IPC-токены двух направлений различны; токен центра не передаётся decoy.

## Воспроизведение проверок

Нужны Go 1.26.0+, Docker и отдельная тестовая PostgreSQL. Например:

```sh
docker run --name hf-be02-test-db --rm -d \
  -e POSTGRES_PASSWORD=be02-local-test \
  -e POSTGRES_DB=honeyforge_test \
  -p 127.0.0.1:55432:5432 postgres:17-alpine
docker exec hf-be02-test-db pg_isready -U postgres -d honeyforge_test
export TEST_DATABASE_URL='postgres://postgres:be02-local-test@127.0.0.1:55432/honeyforge_test?sslmode=disable'
go test -count=1 ./...
go test -race -short -count=1 ./...
go vet ./...
go build ./...
git diff --check
```

Дождитесь готовности БД перед тестами. Тесты создают и удаляют собственные схемы.
Без `TEST_DATABASE_URL` PostgreSQL-проверки пропускаются. `-short` пропускает
длительный тест разрыва и сборку/перезапуск бинарного агента; обычный прогон
включает оба. Точный длительный сценарий:

```sh
go test -count=1 -v ./internal/control -run '^TestBE02'
```

## Границы проверки

Сценарии выполняются локально через TLS и настоящую PostgreSQL. 60-секундный
разрыв моделируется недоступностью management API, а не изменением маршрутов
внешней сети. Проверка firewall/MASK-1 на отдельном хосте относится к приёмке
deployment BE-04/QA-03 и здесь не заявляется выполненной.

Если процесс прерван между вызовом decoy и сохранением результата, исход
операции может быть неизвестен. Агент отправляет `failed` с диагностикой
`command outcome unknown after interruption` и не повторяет действие вслепую.
Нужно проверить фактическое состояние decoy и при необходимости создать новую
команду. Это исключает ложный успех и повтор побочного эффекта. Журнал ограничен
10 000 командами; подтверждённые записи старше TTL + 24 часа очищаются при
добавлении новых. Один файл состояния/очереди предназначен одному процессу агента.

Quarantine не имеет автоматического удаления или UI редактирования. При
обслуживании остановите агент, сохраните приватную копию SQLite и разберите
причину; не удаляйте события для сокрытия ошибки. Физическое отключение питания
диска не моделировалось; проверены WAL recovery после SIGKILL и SQLite FULL.
