# План реализации BE-01

Этот документ описывает границы и порядок работ по [задаче #1](https://github.com/fezonV/HoneyForge/issues/1). Существующий прототип в корневом `main.go` остаётся отдельным приложением и продолжает хранить журнал событий в памяти.

## Объём и решения

Приложение `cmd/control` запускает Control API с хранением в PostgreSQL. Минимальная версия Go для модуля — 1.26; разработка и проверки выполнялись на Go 1.27.2. Для PostgreSQL используется `pgx/v5`, пароли операторов хранятся в виде bcrypt-хешей. Маршруты `/api/v1` предназначены для операторов, а `/agent/v1` — для регистрации агента и чтения назначенной ему конфигурации. Старые незаверсионированные макеты API этим приложением не используются.

Профили можно повторно назначать разным ловушкам. Каждое изменение имени, описания или конфигурации создаёт неизменяемую ревизию. У ловушки отдельно хранятся желаемая и фактически применённая ревизии; назначение новой версии не объявляет её применённой до подтверждения агентом. Удаление профиля логическое, поэтому история сохраняется.

Сессионные и CSRF-токены хранятся в PostgreSQL только в виде SHA-256-хешей. Есть роли `operator` и `viewer`. Изменяющие запросы требуют роль оператора, совпадение `Origin` с настроенным источником (если заголовок передан), CSRF-cookie и такое же значение в `X-CSRF-Token`. Обычные ответы скрывают синтетические пароли; их отдельное чтение доступно только оператору и попадает в аудит. Токен агента независим от операторской сессии и связан с одной ловушкой. Токен регистрации действует десять минут, используется один раз и возвращается только при выпуске.

Команда сохраняет ожидаемые профиль и ревизию, имеет срок жизни от 1 до 3600 секунд и на этом этапе остаётся в состоянии `queued`; просроченные записи помечаются `expired`. Доставка, исполнение и изменение фактически применённой версии относятся к задаче #2.

## Этапы реализации

1. **Контракты, настройки и база данных.** Описать шаблоны, профили и ревизии, ловушки, агентов, команды, события, сессии посетителей, ошибки API и уведомления WebSocket; добавить валидаторы, примеры, OpenAPI, миграции PostgreSQL, проверки состояния и локальную Compose-конфигурацию с публикацией портов только на loopback.
2. **Вход, роли и аудит.** Добавить создание пользователей через CLI без стандартной учётной записи, bcrypt, восьмичасовые серверные сессии, отзыв при выходе, разграничение ролей, ограничение попыток входа и аудит значимых действий.
3. **Профили и ревизии.** Реализовать создание, чтение, список, изменение и логическое удаление профилей, а также чтение истории. Проверять ограничения HTTP-конфигурации, скрывать синтетические пароли в обычных ответах, отдельно и с аудитом выдавать чувствительную ревизию. При устаревшем `base_revision` отвечать `409`.
4. **Ловушки, регистрация агентов, очередь и приёмка.** Реализовать список и фильтры ловушек, точное назначение или отвязку ревизии, одноразовую регистрацию и привязанные к ловушке credentials агента, чтение назначенной конфигурации, запись команд с TTL и чтение аудита оператором. Затем выполнить PostgreSQL-тесты, сборку, `vet`, проверки с `-race` и проверку сохранности данных после перезапуска.

## Проверки

```powershell
$env:Path = 'C:\путь\к\Go\bin;' + $env:Path
go build ./...
go vet ./...
go test ./...
```

Для интеграционных проверок PostgreSQL задайте `TEST_DATABASE_URL`, указывающий на отдельную тестовую базу. Набор создаёт в ней схему со случайным именем и по завершении удаляет только эту схему; сама база не очищается и не удаляется. Если переменная не задана, интеграционная проверка выводит причину пропуска.

## Что не входит в BE-01

В этой задаче ещё нет heartbeat и доставки/подтверждения команд, процессов приманок, приёма и дедупликации событий, сессий посетителей, постоянной очереди агента, WebSocket и сформированного комплекта развёртывания. Схемы будущих сообщений зафиксированы в OpenAPI и `examples/*.future.json`. Это следующие этапы проекта; текущая реализация не выдаёт их за готовые функции.
